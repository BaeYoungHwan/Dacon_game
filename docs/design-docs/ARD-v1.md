## 2. 아키텍처 제약사항

### 기술적 제약
- 클라이언트 사이드 렌더링(CSR)만 허용 — SSR 금지
- 게임 데이터(종목, 뉴스 이벤트)는 JSON 파일로 하드코딩 — 외부 API 호출 금지
- Supabase는 랭킹 보드 단일 목적으로만 사용

### 조직적 제약
- 2인 팀 (신입 포함) — 신입이 이해 가능한 코드 복잡도 유지
- 5일 스프린트 — 오버엔지니어링 금지, 실용성 우선

### 예산/인프라 제약
- Supabase Free Tier 범위 내 운영 (랭킹 수천 건 수준)
- Vercel Hobby Plan으로 배포

## 3. 주요 아키텍처 결정 (초안)

| 결정 영역 | 선택 | 근거 |
|-----------|------|------|
| 상태 관리 | Zustand | Redux 대비 보일러플레이트 최소, 신입 학습 곡선 낮음 |
| 스타일링 | Tailwind CSS | 빠른 UI 구현, 반응형 처리 용이 |
| 백엔드 | Supabase (랭킹만) | 서버리스, 무료 티어, SQL 직관적 |
| 배포 | Vercel | GitHub 자동 배포, 프리뷰 URL, 무료 |
| 빌드 도구 | Vite | 빠른 HMR, React 18 지원 |
| 데이터 지속성 | Local Storage | 서버 의존 없이 새로고침 복구 |
| 라우팅 | 조건부 렌더링 | 단순 3페이지 — react-router 오버엔지니어링 방지 |

## 5. 검증 기준

아키텍처가 이 ARD를 만족하는지 확인하는 방법:

- [ ] Lighthouse 퍼포먼스 90+ 달성
- [ ] 모바일(375px) 레이아웃 정상 표시
- [ ] 새로고침 후 게임 상태 복구 확인
- [ ] Supabase 랭킹 등록/조회 정상 동작
- [ ] 전체 게임 플레이타임 15~20분 내 완료 확인
- [ ] Supabase anon key 코드 직접 노출 없음 확인
